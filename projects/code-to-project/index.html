From Code To Project:

Building Scalable Software.

How to turn a one-file classroom assignment into a large project that other people can build, change, test, and ship.

Armen Deroian · IHEARTCOMPUTER · November 4, 2026

0101 / why it matters

"It works on my machine"

Famous last words. You can build and run the project on your machine, but your teammate cannot.

“Module not found”
You installed something globally and forgot to record it.
“What command do I run?”
The steps are in your memory, not in the repository.
“Where is the data?”
Your code assumes a file, local server, or environment variable exists.
0201 / why it matters

The five promises of a real project

A new contributor should be able to answer five questions without calling the original author.

  1. Understand: What does the app do, and where does the important logic live?
  2. Run: What environment and commands reproduce it locally?
  3. Change: How can I make one feature safely?
  4. Verify: How do I know I did not break something?
  5. Ship: How does tested code become a release?

Project structure, Git, dependency management, builds, tests, and pipelines each solve part of that contract.

0301 / why it matters

Presentation example: a campus events application

We will scale one imagined application from a script that lists campus events into a small, maintainable project. We will revisit this same imagined project in each chapter.

Now: one script

Read a JSON file, filter events by day, print results in a terminal.

Later: a product

Reusable event logic, an API or UI, persistence, tests, and a documented release process.

  1. Code → isolate responsibilities
  2. Structure & Git → collaborate on changes
  3. Build & packages → make setup predictable
  4. Tests → catch regressions
  5. CI/CD → automate verification and release
0402 / structure

The "one-file" solution

There is nothing inherently wrong with one file. It becomes a problem when input, business rules, and storage become difficult to change independently.

# campus_events.py - simplified starting point
    import json
    from pathlib import Path

    records = json.loads(Path("events.json").read_text())
    requested_day = input("Event date (YYYY-MM-DD): ")

    for event in records:
        if event["date"] == requested_day:
            print(event["title"])

Hidden assumptions: execution starts in a specific directory, the JSON file exists, and every event has a date and title.

Our first refactor is not to randomly create folders, but to create groups of meaningful ownership and responsibility.

0502 / structure

Split by ownership & responsibility, not by file length

Domain logic
Rules about events: filtering, validation, duplicate detection. Ideally unaware of the terminal or database.
Input / output
CLI commands or HTTP routes. Translate user input into calls to domain logic.
Infrastructure
Read JSON, query a database, or call another service. These details can change independently.

A module groups related code. A package makes code importable or distributable. An application is the runnable product. These concepts overlap but are not interchangeable.

If the app gains a web page tomorrow, should event filtering be rewritten?

0602 / structure

A small project needs a small structure

Important: this is an example layout for the campus events Python app and is not a universal template.

campus-events/
    ├── README.md                   # what, requirements, commands
    ├── pyproject.toml              # metadata, dependencies, tools
    ├── uv.lock                     # resolved dependencies
    ├── .python-version             # runtime choice
    ├── .gitignore                  # local/generated files to omit
    ├── .env.example                # safe configuration example
    ├── data/events.example.json   # non-sensitive sample data
    ├── src/campus_events/
    │   ├── __init__.py
    │   ├── cli.py                  # terminal entry point
    │   ├── events.py               # domain rules
    │   └── storage.py              # persistence
    ├── tests/test_events.py
    └── .github/workflows/ci.yml

Guideline: start with the smallest arrangement that makes navigation obvious; introduce subpackages only when a genuine boundary appears.

0702 / structure

Put the behavior behind a reusable function

# src/campus_events/events.py

    def events_on_date(events: list[dict], day: str) -> list[dict]:
        """Return events whose ISO date equals day, preserving order."""
        return [event for event in events if event["date"] == day]

Now the CLI and a future web route can both call events_on_date. The function has no terminal prompts, filesystem reads, or HTTP objects.

# Conceptual call flow
    CLI:  parse arguments -> events_on_date(...) -> print results
    API:  parse request   -> events_on_date(...) -> return JSON

Contract to document: dates are YYYY-MM-DD strings, records have a date key, and invalid input is validated at the boundary. Decide what the function promises before optimizing it.

0802 / structure

Folders, monorepos, and multiple repos are different decisions

Choose repository boundaries based on change patterns, ownership, and releases.
LayoutGood fitTrade-off
One application / one repoA CLI, website, or service with one release cycleSimple to navigate; avoid inventing packages before they help
Monorepo / several projectsWeb + API + shared contracts that change togetherEasy atomic changes; more workspace/build coordination
Multiple repositoriesIndependently owned, secured, or released componentsClear release boundaries; cross-repo compatibility work

Neither a monorepo nor microservices are requirements for “production quality.” You can run a very large application from one repository.

1002 / structure

README: your first teammate’s first five minutes

Write the instructions for someone who knows the language but knows nothing about your laptop.

  1. Purpose: one paragraph, plus a screenshot or small usage example if useful.
  2. Prerequisites: supported runtime, package manager, database or system tools.
  3. Setup: one reliable install command and a safe .env.example.
  4. Work loop: commands to run, test, lint, build, and reset local data.
  5. Contributing: where to change a feature and how to propose it.

Include sample data and migrations if needed. Do not assume local credentials or production resources.

Checkpoint: could someone who missed today’s talk start the project using only this file?

1103 / git

Git turns edits into inspectable history

Git is version control; GitHub and GitLab are collaboration platforms built around Git repositories.

# For a new, unversioned project
    git init
    git status

    git switch -c feature/date-filter
    # edit events.py, tests, and README
    git diff
    git add src/ tests/ README.md
    git diff --staged
    git commit -m "Add date filtering for campus events"

    # After adding a remote named origin
    git push -u origin feature/date-filter

Open a pull request with what changed, why, and how it was tested. Review the diff before staging. Use your team’s branching and merge convention.

The unit of collaboration is a small, understandable change, not a week-long mystery commit.

1203 / git

"Oh no! The Intern committed the .env file" - Use .gitignore

Commit

Source, tests, README, configuration, project metadata, lockfiles for applications, migrations, and safe fixtures.

Ignore

Virtual environments, downloaded dependencies, caches, logs, generated builds, credentials, and machine-specific settings.

# Example .gitignore - choose entries that match your stack
    .venv/
    __pycache__/
    .pytest_cache/
    .ruff_cache/
    node_modules/
    dist/
    build/
    .env
    .env.*
    !.env.example

.gitignore does not untrack existing commits. Use git rm --cached <path> to stop tracking a file. A leaked token must be revoked or rotated even if you later delete its file.

1303 / git

A pull request is more than a merge button

  1. Create a focused branch and commit.
  2. Explain the intended behavior and link the issue or requirement.
  3. Verify by running local checks and reading the CI results.
  4. Review interfaces, test cases, documentation, and unintended changes.
  5. Merge when required checks pass; keep the main branch releasable.

Example PR description: “Adds optional event-date filtering to CLI output. Updated tests for matching and non-matching dates. Verified with uv run pytest.”

What would you expect a reviewer to ask if the filter uses your computer’s local timezone?

1404 / build systems

What is a build system actually doing?

A build is a repeatable transformation from inputs to outputs. A build system coordinates the steps and their dependencies.

Inputs
Source files, configuration, dependencies, assets, compiler/runtime versions.
Tasks
Generate code, compile, link, bundle, optimize, validate, package.
Outputs
Executables, dist/ sites, wheels, JARs, or container images.

Some languages interpret source directly. They still need tasks for linting, testing, packaging, and deployment. A development server is not the same as a production build.

1504 / build systems

A dependency graph saves time and prevents bad ordering

# Conceptual C++ target graph
    src/events.cpp --> events.o --+
                                +--> link --> campus-events
    src/main.cpp   --> main.o ----+
# CMake configures a build; Ninja/Make execute it
    cmake -S . -B build -G Ninja
    cmake --build build

If only events.cpp changes, an incremental build may recompile it and relink, rather than rebuild everything. This depends on accurate dependency tracking.

Other examples: Vite bundles client assets; Gradle orchestrates JVM tasks; Cargo resolves Rust dependencies and builds crates. Some tools combine roles.

Reference: CMake tutorial.

1604 / build systems

Project commands are a public interface

Developers, editors, and CI should be able to run the same named operations.

// Teaching example: package.json script definitions
    "scripts": {
      "dev": "vite",
      "build": "vite build",
      "check": "tsc --noEmit",
      "lint": "eslint .",
      "test": "vitest run"
    }

npm run dev starts a local work loop; npm run build creates the distribution; npm test runs automated checks. The real personal-website manifest provides a similar developer command surface, using Svelte-specific checking.

Also document where the artifact lands, how to preview it, and which operating systems and runtimes are supported.

1805 / packages & tools

A manifest is the shopping list; a lockfile is the receipt

Manifest
Declares direct packages, allowed versions, project metadata, and sometimes executable tasks.
Lockfile
Records the resolved dependency graph at versions chosen by the package manager.
Runtime / environment
Specifies interpreter, compiler, OS/system libraries, services, and configuration.
# Simplified Python pyproject.toml fragment
    [project]
    name = "campus-events"
    version = "0.1.0"
    requires-python = ">=3.12"
    dependencies = []

    # uv.lock: generated by uv; commit for this application
    # .python-version: selected interpreter version

The lockfile makes application installs more predictable, but it cannot pin your OS, native toolchain, external APIs, or secrets. Do not manually edit generated lockfiles.

1905 / packages & tools

One setup path: from script to Python project

For our running example, uv can initialize project metadata, manage a local environment, and create a lockfile.

# One-time project setup; run outside an existing project
    uv init --package campus-events --python 3.12
    cd campus-events
    uv add --dev pytest ruff

    # Move your event logic into src/campus_events/
    # Add test files under tests/

    # Day-to-day work
    uv sync --locked
    uv run --locked pytest
    uv run --locked ruff check .
    uv build                    # creates distribution files in dist/

The initialization command creates starter files; you still need to implement the real CLI, logic, and tests. On an existing project, read its README and use its chosen package manager rather than re-initializing it.

Reference: uv project initialization, locking and syncing.

2005 / packages & tools

The same idea in four languages

# JavaScript / TypeScript, with package-lock.json
    npm ci
    npm run build

    # Python, with uv.lock
    uv sync --locked
    uv run --locked pytest

    # Rust, with Cargo.lock
    cargo build --locked
    cargo test --locked

    # Java, with the project Gradle wrapper
    ./gradlew build

npm ci expects a lockfile and rejects a manifest mismatch; uv --locked rejects an outdated lockfile. Gradle dependency locking is available but is not automatically enabled for every project.

Before adding a library, consider its maintenance, license, transitive dependencies, and security posture. Install only what the project needs.

References: npm ci, uv sync, Cargo, Gradle dependency locking.

2105 / packages & tools

The development environment is bigger than dependencies

Editor + language server
Completion, navigation, refactoring, diagnostics. Examples: VS Code, IntelliJ IDEA, clangd, Pyright.
Formatter + linter
Consistent formatting and automated code-quality feedback. Examples: Prettier, ESLint, Ruff, clang-format.
Debugger + profiler
Investigate state and measure slow paths rather than guessing.
Local services
Docker Compose can provide a disposable database or mail server, without hardcoding production credentials.

Application package manager ≠ machine package manager. npm or uv installs project dependencies; apt, Homebrew, or winget installs machine-level tools.

Which tools must be on every contributor’s computer, and which can the project supply?

2206 / testing

A test specifies behavior, not implementation

Once the event logic is a pure function, checking it is cheap and repeatable.

# tests/test_events.py - runnable with pytest
    from campus_events.events import events_on_date

    def test_matching_day_is_included():
        events = [
            {"title": "Club night", "date": "2026-11-04"},
            {"title": "Hackathon", "date": "2026-11-05"},
        ]
        assert events_on_date(events, "2026-11-04") == [events[0]]

    def test_no_matches():
        assert events_on_date([], "2026-11-04") == []

A good test names a promise and checks its result. Add cases for empty inputs, invalid records (if validation is in scope), duplicates, date boundaries, and previously reported bugs.

2306 / testing

Different tests protect different boundaries

KindCampus events exampleWhat it catches
UnitFilter a small list by dateIncorrect business logic
IntegrationSave an event and load it from temporary storageBroken interaction with database/file layer
End-to-endOpen the site, submit an event, see it in a listA user workflow failing across systems
Static checksRun type checker, linter, formatter checkProblems tests may not exercise

A sensible progression: many fast unit tests, focused integration tests, and a smaller number of slower browser journeys. Do not use production accounts, clocks, or live third-party APIs in ordinary unit tests.

Coverage is a clue, not a quality score. Executing a line does not guarantee an assertion checked the correct behavior.

2406 / testing

Reproduce → fix → prevent recurrence

  1. Describe the bug using a concrete input and expected output.
  2. Write a test that fails for the bug.
  3. Fix the code with the smallest clear change.
  4. Run the focused test and the wider project checks.
  5. Commit the fix and regression test together.

Example: students in different time zones see the same event on different calendar days. The real problem might be an inconsistent interpretation of a timestamp, not the filtering loop itself.

What is the difference between a calendar date (“Nov 4”) and a timestamp (“Nov 4 at 9 PM UTC”)? Where should that rule be defined?

2507 / ci / cd

CI is your project on a computer that knows nothing about you

Continuous integration runs a documented set of checks when code is pushed or proposed for merging.

commit / pull request
            |
       fresh checkout
            |
       install runtime
            |
      install locked dependencies
            |
      lint + type check -> tests -> build
            |
         pass / fail
            |
          review & merge

A local green test is useful. A clean CI run also reveals missing setup steps, uncommitted files, and environment-dependent assumptions.

Popular orchestrators: GitHub Actions, GitLab CI/CD, Jenkins, Azure Pipelines. Jobs generally run in isolated workers and expose logs and statuses.

2607 / ci / cd

A working starter GitHub Actions workflow

This is actual workflow YAML for the Python example-not pipeline pseudocode. It assumes the generated Python project, uv.lock, Ruff, and pytest have been committed.

# .github/workflows/ci.yml
    name: CI

    on:
      pull_request:
      push:
        branches: [main]

    permissions:
      contents: read

    jobs:
      verify:
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v7
          - uses: astral-sh/setup-uv@v9
            with:
              enable-cache: true
          - run: uv python install
          - run: uv sync --locked
          - run: uv run --locked ruff check .
          - run: uv run --locked pytest -q
          - run: uv build

For higher supply-chain assurance, pin actions to full commit SHAs and manage upgrades deliberately. Protect the default branch with required status checks.

References: uv on GitHub Actions; workflow syntax.

2707 / ci / cd

Real case study: a publication with multi-stage checks

The armen-articles repository is an Astro publication. Its CI workflow separates a validation/build job from a dependent browser-test job.

  1. Validate: npm ci → type/content checks → lint → format check → unit tests → production build → integration/link tests.
  2. Store artifact: upload the built dist/ directory.
  3. Browser tests: download that artifact, install Chromium, run Playwright, preserve a failure report.

Cache vs artifact: a dependency cache speeds repeated work; a build artifact carries a specific result between jobs.

Source: CI workflow and package scripts.

2807 / ci / cd

CI, delivery, and deployment are not synonyms

Continuous integration
Every proposed change is built and checked frequently.
Continuous delivery
Passing changes are kept release-ready; production promotion may require approval.
Continuous deployment
Passing changes are automatically promoted to production without a routine manual release decision.
proposed change -> CI checks -> tested artifact
                                      |
                                   staging
                                      |
                               approval (optional)
                                      |
                                   production
                                      |
                              smoke test + monitor

For armen-articles, a separate workflow triggers on pushes to main and manual runs, repeats several checks, then deploys with Wrangler. It does not depend directly on the full CI browser-test job; that is a meaningful release-gating decision.

Source: deployment workflow.

2907 / ci / cd

A release is not done when the upload finishes

  1. Deploy to an explicitly chosen environment using least-privilege credentials.
  2. Verify with a smoke test: does the app load and perform one critical task?
  3. Observe structured logs, errors, latency, and health checks.
  4. Recover by rolling back the app or promoting the previous known-good artifact when possible.

Keep secrets out of builds from untrusted pull requests. Use protected environments where appropriate. Database migrations need separate compatibility and backup plans: rolling back code does not automatically reverse changed data.

The simplest reliable deployment is better than an impressive pipeline nobody can debug.

Professional engineering is choosing the smallest tool that makes the next change safer. There is no award for the most YAML files.

3108 / next steps

The real finish line

Can somebody who has never met you clone your project, get it running, make a small improvement, verify the change, and trust the release process?

When the answer is yes, you have moved beyond “code that runs” toward software that can be maintained.

Make it understandable. Make it reproducible. Make it testable. Then make it releasable.

One action to take tonight: improve the README of a project you already wrote.
