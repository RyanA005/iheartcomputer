what people use

for one request, the common answers are variants of a waterfall (time on X, one row per span). references:

  • Chrome DevTools Network waterfall: flat request list; bar segments for queue / connect / wait / download
  • DebugBear request waterfall: same idea with filmstrip context
  • Grafana span waterfall: nested parent/child tree; optional critical-path shading
  • Honeycomb trace waterfall: summary strip + full tree
  • AppSignal trace timeline: tree gutter + duration column
  • Middleware and similar APM UIs also ship a flame chart (time on X, depth on Y) beside the waterfall

below: six renderings of our capture. none are punchlines; all are candidates for the talk figure.

1 chrome-style 2 nested spans 3 swimlanes 4 flame chart 5 composition 6 critical path

1. Chrome / DebugBear-style waterfall

flat list, start-time order. each bar is wait (light) + body (dark). good for “what ran in parallel?”. weak on parent/child.

2. Nested span waterfall (Jaeger / Grafana / Honeycomb)

indent shows call tree: client, function, board|badges, HTTP. industry default for APM. denser left gutter.

3. Machine swimlanes

one lane per machine (laptop / app Node / Supabase). answers “whose metal?” first. parallel spans share a lane.

4. Flame chart (icicle)

time on X, nest depth on Y. width = duration. compact overview; harder to label every HTTP call.

5. Time composition (stacked bars)

not a timeline: where the ms went as exclusive buckets. honest about estimates; loses overlap/order.

6. Critical-path Gantt

Grafana-style: full span bars in mute, critical path (serial chain that sets TTFB) in ink. shows what you could shorten.

how to use this page
